Goal

    Not fixed in this run — and nothing false got through.

    Every attempt that reached a booked page while the booking was saved, or reopened, with the wrong date was rejected.

    The recorded timeline names the code behind it: right after the date is typed, the month-change handler in booking.js requests get_unavailable_dates, and the response handler overwrites the field with the first free day. Reopening a booking then resets the date to today when Next is pressed. Agent versions 4 and 5 fixed both, with no diagnosis supplied, in 2 of 10 runs — see every run.

    A loop that ends at the saved outcome, not the success page.

    1. ObserveA real browser drives the journey with the keyboard only and records where focus goes and where it gets stuck.
    2. Diagnose & repairNemotron 3 Super reads the evidence and the source, finds the cause and writes exact code edits. It is never told the cause.
    3. Verify for realEach patch that applies is built in a fresh, offline sandbox. The booking is made, read back from the database with a read-only account, and reopened in a fresh browser.
    4. Feed backIf anything is off — a build error, a stuck key, a wrong saved value, a broken mouse path — the evidence goes back to Nemotron and it tries again.

    Why not just check the confirmation page?

    Because it lies. In our runs, — AI fixes reached a booked confirmation while the booking was saved, or reopened, with the wrong date. In the phone case the page says booked while the database holds 0000000000, and a patch that hardcodes the test number would fail when a second customer types 0000000073. AccessFinish checks all of it.

    Why keyboard journeys?

    Millions of people navigate with a keyboard or assistive technology. A form that "loads" but can't be completed locks them out, and accessibility law in the EU and US now expects it to work.
